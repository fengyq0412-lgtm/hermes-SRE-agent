# Hermes SRE Agent

面向 AI 与 Web 服务的、**证据优先、审批受控**的 SRE 智能体。

```text
观察 → 诊断 → 制定计划 → 人工审批 → 修复 → 验证
```

Hermes 的目标不是抢先猜出答案，而是把每条结论和真实采集结果关联起来；任何会改变状态的操作，都不能绕过人工审批。本仓库包含可复现的故障诊断链路、本机只读采集、受控运维变更命令、诊断评测、多角色分诊与事件记忆，以及 V0.5 平台观测接入。

## 一分钟演示

```bash
# 建立 Python 3.9+ 虚拟环境（首次执行）
python3 -m venv .venv
source .venv/bin/activate

# requirements.txt 会以可编辑模式安装本项目及命令行入口
pip install -r requirements.txt

# 无需模型密钥的确定性演示
hermes "legal-agent 最近很慢，帮我排查原因" --mode rules --scenario api_slow
```

## Agent 模式：像 Codex 一样从终端自然语言开始

Hermes 默认进入 Agent 模式。你只需启动终端并描述问题；模型会在只读工具白名单中自主选择健康检查、日志、Docker、GPU、Git 变更或代码差异审查工具。模型不能获得任意 Shell、写文件、重启服务或删除资源的权限。

Hermes 使用 OpenAI Chat Completions 兼容协议，因此可以对接任意提供该协议的国内或本地模型服务。将模板复制为根目录 `.env`，然后填写供应商地址、密钥和模型名：

```bash
cp .env.example .env
# 编辑 .env 后，Hermes 会在启动时自动读取它

# 单次自然语言诊断
hermes "昨天部署后 legal-agent 接口从 800ms 变成 4 秒，帮我排查"

# 连续对话式终端
hermes --interactive
```

连接本地兼容服务时，可使用 `http://localhost:端口/v1` 或 `http://127.0.0.1:端口/v1`。远程模型地址必须使用 HTTPS，避免 API 密钥以明文传输。

## 本地控制台：项目选择、代码审查与修复

Hermes 提供本地项目 Agent：在页面选择项目文件夹，输入「帮我检查这个项目有哪些 bug」或「修复 main.py 的边界错误」，Agent 会自动选择审查或修复流程。可以继续追问，例如「第二个问题在什么条件下触发？」。需要将修复写回项目时会弹出审批请求；批准后当前任务继续执行。

任务会按本次要求区分完成条件，页面显示所选模式：

| 你的要求 | 行为与完成条件 |
| --- | --- |
| 「检查有哪些 bug」「怎么修复」「只给建议，不要改代码」 | 只读分析，读取证据后给出解释或建议，不产生修改审批 |
| 「请修复这个 bug」「修改 main.py」「就按上面的方案改」 | 执行修改，必须在临时副本形成实际补丁，再验证并请求人工审批 |
| 修改请求无法执行，或模型一直只给文字建议 | 显示「修改任务未完成」和阻碍，可继续追问；不会冒充已完成 |

执行修改时，系统会检查实际文件净变更；空替换、改完又改回、只输出代码块均不能满足完成条件。模型提前结束且没有补丁时，最多纠正两次，要求继续调用编辑工具。工具预算仍有限，不会无限循环。缺少明确目标、不支持的文件类型或无需合理修改时，应说明依据，不能为满足补丁条件制造无关改动。意图分类格式异常且无法确定修改授权时默认只读，用户可继续明确要求修改。

模型报告受阻时，编排器会进行一次复核，要求核对当前代码、身份来源、相关实现及历史约定；预算紧张时至多追加四次工具调用。找不到现成的校验函数不等于不能开发：用户已明确规则时，可在已有 Python 业务文件中新增函数并接入调用。权限主体、资源归属或放行规则确实没有定义时，Agent 应返回一到三个具体澄清问题，页面显示「需要确认业务规则」；直接在当前会话回答即可继续。Hermes 不应自行猜测权限规则，也不会把恒真校验当作完成。工具能力限制仍会明确报告为未完成。

源码查询提供 `search_code({text})` 跨文件字面搜索，以及 `resolve_symbol({name})` 静态定位 Python 定义和 `from ... import ... as ...` 别名。模型把“没搜到同名定义”当成“函数不存在”并准备询问用户时，程序会先核对别名及目标模块定义；若能定位，会将文件、行号和必要源码片段交还模型继续处理。静态定位不执行项目代码；动态导入和生成的符号仍可能无法解析，未匹配不等于已证明不存在。

取证预算耗尽但尚无修改时，会进入独立的补丁生成阶段，最多调用模型三次。此阶段不再执行浏览工具，要求基于已读取源码提交 `patch` JSON，包含 `changes` 精确替换列表和修改说明；最多 12 处替换、5 个已有业务文件。整批替换失败会恢复临时副本，再要求模型纠正。成功生成净变更后照常运行沙箱、展示 diff 并等待人工审批；没有有证据的可修复问题时仍应明确说明，不为产生补丁而制造无关改动。

```bash
# 从 Hermes 项目目录启动
hermes-web
```

### 网页运行诊断（只读）

在输入框上方将「任务类型」切换为「运行诊断（只读）」，明确填写实际**服务名、Docker 容器名和 HTTP 健康检查地址**，再输入故障描述。三个目标都没有 `legal-agent` 默认值；缺少或格式不合法会在后台采集前拒绝。先选择与服务对应的项目：该目录只用于 Git 变更线索，不会被运行诊断修改。请确认健康检查地址确实存在，不能把示例地址当成已部署端点。

默认「规则分诊」无需模型密钥，读取本机 HTTP、Docker、系统/GPU 与所选项目的 Git 线索；也可选「模型辅助」，让模型在已启用的只读工具中选择证据，此时采集结果会发送到 `.env` 配置的模型服务。展开「可选：Kubernetes / Prometheus / Grafana」后，可按需填写 context、namespace、selector、Prometheus 根地址与 job、Grafana 根地址与令牌**环境变量名**。成组参数必须填全；Grafana 令牌值只在服务端环境变量或 `.env` 中设置，不输入网页。运行结果、目标参数与摘要会保存在本机会话；原始平台响应不单独写入会话库，但诊断报告可能包含容器日志片段，请按敏感数据管理。页面不会执行重启、配置修改或代码写回。

规则分诊会把 Kubernetes 副本不足、Pod 异常以及 Prometheus `up=false` 记为附带来源和同现证据的候选线索，并纳入假设与后续验证建议；它们不会单独提高根因置信度。Grafana 当前只读取已配置规则，不代表规则正在触发，也不会被当作故障证据。

模型辅助诊断会先校验每次工具调用的参数，错误调用记为失败采集并允许模型在本轮步骤内纠正。报告中的观察结果由实际工具返回值提取；目前只有目标容器已停止、日志明确报告缺少必需环境变量、以及高延迟与 GPU 显存压力和排队同时出现这三类信号可按程序规则复核。其他模型根因结论会降为低置信度的待验证假设，不会据此生成具体修复操作。

升级已有安装后需重启 `hermes-web`，再刷新页面才能使用新接口。没有 Docker、kubectl 或平台凭据时，相应采集项会如实显示失败；这不等于已确认服务故障。

项目列表保存在启动目录的 `.hermes/projects.json`，会话保存在 `.hermes/conversations.sqlite3`，均在重启后保留。刷新页面会恢复选中的项目会话和执行状态。运行日志会另外保存到本地（见下节）。网页问答不往被审查项目写报告。选择没有 Git 历史的项目也能直接审查源码。

## 多轮对话与记忆

每个项目可以有多个独立会话。后台根据会话标识读取历史，不接受页面伪造的聊天内容。原始问题、回答、执行状态、用量、diff 和测试结果持久化到本地 SQLite；源码读取结果不整段重复存储，只保留文件与行号索引。已结束会话可在侧栏删除，删除会同时清除对应的 SQLite 记录和本机 JSONL 运行轨迹；正在运行或等待审核的会话不能删除。刷新恢复正在进行的任务；服务重启后中断任务会明确显示中断，待审批补丁失效，需重新生成并验证，不能恢复旧写回权限。

默认上下文由最近 **3 轮问答**、更早历史的**增量摘要**和近期**工具证据索引**组成，总历史内容限制为 **24000 字符**。窗口滑动时只压缩刚移出的轮次并更新旧摘要，摘要调用的 token 也计入本轮用量。摘要失败会退回原文摘录，长消息按预算缩略，完整记录仍保存在会话库中。意图判断与执行 Agent 使用同一份历史，避免分类器只记得上一句话。

Agent 可调用 `search_history({text})` 检索当前会话的原始用户要求和助手回复，找回摘要遗漏的细节。工具索引只帮助定位，历史模型建议不等同于真实代码现状；生成补丁前仍须读取当前源码。摘要有损，无法保证无限保留每个细节；项目之间、同一项目的不同会话之间不自动共享记忆。

每条回答的「本轮上下文」可查看实际带入的近期轮数、已压缩轮数、字符数和摘要；运行日志同时记录 `context_prepared`。`.env` 可设置 `HERMES_CONTEXT_RECENT_TURNS`（1–10，默认 3）与 `HERMES_CONTEXT_MAX_CHARS`（8000–64000，默认 24000）。这是历史上下文的字符预算，不含系统提示、本轮提问和本轮工具输出，也不是供应商的 token 计费。

会话库位于 Git 已忽略的 `.hermes/` 中，文件默认仅本机用户可读写。由于要恢复原始问答及 diff，库中可能包含用户主动输入或模型回答中的敏感内容，请按项目数据管理。此功能启用前未保存的旧会话无法由摘要日志完整还原。

服务只监听本机回环地址，并验证页面会话令牌。密钥仅在 Python 服务端使用；`.env` 已被 Git 忽略。**点击发送会将相关源码片段发送至你在 `.env` 配置的模型服务**；工具默认排除隐藏文件、`.env`、凭据文件、依赖目录、生成文件和符号链接，但不等同于完整的源码秘密检测。

源码审查单次最多调用 10 次工具，之后预留两次模型调用生成最终报告；最多列出 500 个文件，每次最多读取 200 行，超出范围会提示截断。报告要求给出总体风险等级、已确认问题、待验证风险和审查范围。没有确凿缺陷时仍会说明残余风险，但不会把猜测写成已确认 Bug。若模型两次都不输出结论，页面仍会展示已读取范围和“待评估”的保底报告。回答基于实际读取范围，不代表已覆盖整个项目；只有启用沙箱且工具实际执行后才有测试结果。页面显示简化后的检查进度，最终回答在模型返回后展示，暂非逐 token 输出。

修改任务在取证预算结束后使用独立的补丁提示和已读取的源码片段，不再重复带入整段工具对话；补丁阶段最多允许两次定点补读。模型默认最多输出 4096 token，可在 `.env` 用 `HERMES_MAX_OUTPUT_TOKENS` 设置为 256–16384。若服务商不支持较高上限，仍可能截断；此时日志会记录 `output_truncated`。补丁支持精确文本替换，或仅在模型实际读取的当前版本行号范围内替换整行；同一批次同一文件最多使用一次行号替换。新文件用完整内容生成，支持业务代码和测试。所有改动只进入临时副本，经沙箱验证、人工审核后才可能写回；证据不足时不会为了弹审批而制造修改。

每次审查下方显示本次模型调用的输入、输出及总 token；顶部显示当前服务启动以来的累计值。统计直接使用兼容接口响应中的 `usage.prompt_tokens`、`usage.completion_tokens` 和 `usage.total_tokens`，部分兼容服务的 `input_tokens` / `output_tokens` 也可识别。接口未返回完整用量时会增加“未上报”次数，不会把未知 token 记为 0。用量暂存在服务内存中，重启 `hermes-web` 后累计值清零；具体费用请以模型服务商账单为准。

## Agent 运行日志

每条回答可展开「查看 Agent 运行日志」，按时间查看任务创建、模式选择、每次工具调用及剩余预算、取证结果摘要、结论收束、沙箱验证、人工审批和逐次 token 用量。模型若按协议给出 `reason`，页面会展示一句简短的决策说明；旧模型不返回时会明确标记为未提供。这里记录的是**模型自述与程序实际执行的可观察轨迹**，并不是模型不可见的内部思维链，不应把 `reason` 当成真实推理过程的逐字记录。

每个任务同步写入启动目录的 `.hermes/traces/<任务编号>.jsonl`，一行一条 JSON，包含 `seq`、`time`、`stage`、`event`、`summary`、`details`。例如：

```json
{"seq":4,"time":"2026-09-24T10:30:00.000+08:00","stage":"取证","event":"tool_result","summary":"read_file 完成","details":{"tool":"read_file","reason":"先检查入口处理逻辑","remaining_calls":8,"path":"src/main.py","requested_lines":[1,160],"outcome":"completed","line_count":78,"total_lines":78,"truncated":false}}
```

日志只保存文件路径、行数、数量、状态、用量等摘要；不会主动保存源码片段、工具原始输出、完整模型回复或 API key。模型提供的 `reason` 会截断并过滤常见密钥格式，但不能替代秘密扫描，敏感项目仍应限制本机日志访问。日志文件位于已被 Git 忽略的 `.hermes/` 中；若磁盘写入失败，页面仍会显示当前会话的内存日志与错误提示。可用 `tail -f .hermes/traces/<任务编号>.jsonl` 实时观察，用 `jq` 做统计；重启服务后可恢复已保存的会话，JSONL 也会保留。

`hermes-web` 自身的启动、API 响应、任务阶段和异常会同时写入启动终端及 `.hermes/server.log`。该日志仅记录任务编号、路由、状态码和事件类型，不记录提问正文、查询参数、源码、模型原文或密钥；文件默认仅当前用户可读写。

若补丁未生成，查找同一任务的 `patch_retry`：`error_code` 区分无效 JSON、输出截断、请求了不允许的工具、目标未读、未读取目标行号、精确替换未命中等情况；`reply_chars` 仅记录回复长度，不保存原文。旧日志没有这些字段，因此无法事后准确判断旧任务的具体失败类型。

## Python 测试沙箱

启动 Docker Desktop 后，在 Hermes 项目目录构建一次镜像：

```bash
docker build -t hermes-sandbox:local sandbox
hermes-web
```

刷新页面，直接提问「审查项目并运行 tests 目录中的测试」。Hermes 会根据问题自动决定是否调用沙箱测试；页面可展开查看原始测试输出。

沙箱只复制源码白名单中的文件，排除隐藏文件、`.env`、凭据文件、依赖目录、符号链接和硬链接；这不是内容级秘密扫描，源码里硬编码的密钥仍需自行清除。快照最多 500 文件、单文件 256 KB、总计 20 MB。容器使用非 root 用户、禁网、只读根目录和源码挂载，测试在容器临时副本内执行；限制 1 CPU、512 MB 内存、64 进程、128 MB 临时空间、60 秒和 32 KB 输出。完成、超时或输出超限后均删除本次容器。

默认镜像提供 Python 3.11、pytest、pytest-asyncio、FastAPI、Pydantic、HTTPX，以及文档生成、搜索和当前 `agent-demo` 项目声明的业务依赖；版本约束见 `sandbox/requirements.txt`。更新这些依赖或运行器后需要重新执行 `docker build -t hermes-sandbox:local sandbox`。这些依赖只在构建镜像时安装，项目测试仍在禁网容器运行。不会自动执行被审查项目的依赖安装脚本；其他依赖缺失会展示实际错误，不能据此认定项目有 Bug。项目需要特定版本时，可以自行构建本机镜像并在 `.env` 设置 `HERMES_SANDBOX_IMAGE`，运行时不会自动拉取镜像。原项目不会因测试而修改；Docker socket 和 Hermes API key 不会传入容器。此方案适合本机项目测试，不作为公开多租户运行恶意代码的完整隔离平台。

沙箱是一次性容器：程序在验证时自动创建 `hermes-test-<随机编号>`，执行结束或超时后自动删除，镜像保留供下次使用，不需要在 Docker Desktop 手动启动容器。因此平时只看到镜像属于正常现象。若状态为 `not_run / tests_not_generated`，表示尚未实际创建测试文件，本轮根本没有启动容器；这与 Docker 故障不同。

开发者可运行真实隔离验证：`HERMES_SANDBOX_INTEGRATION=1 PYTHONPATH=src python -m unittest discover -s tests -p test_sandbox.py -v`。

## 修复 Agent 与人工审核

页面只需输入自然语言，例如「修复 main.py 的除零问题，保留现有行为并补充回归测试」。Hermes 先判断本次是代码审查还是修复，再按需要创建过滤快照、修改临时源码并在 Docker 中验证。默认静态查找项目中的 `test_*.py` / `*_test.py` 测试入口，不再要求手动创建 `tests/`。没有可运行测试时，自动进入仅允许修改测试文件的补充阶段，生成针对本次修改的回归测试。数据库调试脚本仅有测试命名但没有测试函数时，不作为默认入口。测试生成失败、依赖缺失或测试失败会如实展示，不能据此批准写回。

测试 Agent 会收到由实际 diff 定位的函数源码、异步标记、路由装饰器、导入信息和相邻辅助定义；必须使用真实字段和返回约定，区分 HTTP 状态码与 JSON 响应体的业务 `code`。普通 pytest 用例可通过 `asyncio.run` 等待异步函数，也支持 `@pytest.mark.asyncio`；运行器只显式启用固定版本的异步插件，其他插件仍不自动加载。同步依赖使用 `Mock`，异步依赖使用 `AsyncMock`。

独立测试生成/纠错不再从项目列表重新探索：编排器预读当前相关源码及允许纠错的测试，登记当前版本的可编辑行范围，然后直接请求测试补丁。最多三次补丁提交、两次定点补读；形成补丁后立即执行沙箱，不再额外调用模型要求文字总结。仅可恢复的模型超时、连接故障、429 或 5xx 在本阶段重试一次；凭据等不可恢复错误不自动重试。请求可能已被供应商计费，重试会额外消耗用量。失败分类以 `test_model_retry / test_generation_failed` 记录，不回显供应商错误正文；审批面板同时显示沙箱错误和“模型纠错未完成”，不会混为单纯的项目依赖问题。

针对导入业务入口连带加载数据库、文档处理等依赖的情况，静态提取未修改的本地模块的真实函数签名、同步类型和定义位置，提供导入前隔离的 fixture 参考。模型必须先确认是外部 I/O 适配器再采用；参考代码进入测试补丁供人工检查，不在宿主机执行。不得替换变更模块、复制被测实现或伪造 FastAPI/Pydantic；真实目标函数、响应模型和包装器仍参与验证。这类单元测试不代表数据库等集成测试通过。未知类、常量、相对导入等不自动推断隔离方式，必要时仍需专用依赖镜像。

单目标、顶层模块的测试生成中，若全部候选依赖都有已知网络/数据库库导入证据，编排器会在临时副本预置 `tests/test_hermes_<目标>.py` 隔离脚手架，并将其纳入人工审核 diff。这是基于静态证据的单元测试边界选择，不证明整个依赖模块只含 I/O；审核时仍需核对隔离范围。真实业务入口通过 `subject` fixture 加载，模型只补充测试用例，可以用 `{path,append_text}` 追加；追加前需读过当前版本末尾。禁止移除脚手架前缀或在测试顶层直接导入目标模块，违规补丁整批回滚。脚手架本身没有测试用例，不能据此启动验证或宣称通过。

独立补丁阶段按消息分别压缩上下文，保留最新失败输出的首尾，避免长源码截掉 `ModuleNotFoundError` 等实际原因。修改导入错误应优先处理导入边界，不能靠改断言或跳过用例掩盖失败。

每个 Agent 阶段单独记录开始时的文件变更。业务阶段已经生成的补丁不能算作测试阶段的产物；测试阶段必须实际形成新增补丁，文字声明不能替代文件修改。业务阶段取证预算用尽但尚无本阶段变更时，进入独立补丁生成阶段。

取证阶段的模型工具请求若出现 JSON 损坏、错误 `type`、未知工具，或 `arguments` 为字符串/数组/null，不再直接抛异常结束任务：将具体格式要求反馈给模型，保留当前上下文，自动纠正最多两次（本阶段累计，不因中间一次成功而重置）。非法请求不执行，不消耗实际工具调用额度；额外模型请求仍计入 token 用量。已有成功修改不重放，文件权限与审批边界不变。日志记录 `protocol_retry` 和 `protocol_retry_exhausted`，不记录错误回复原文。耗尽后安全停止：保留证据和临时补丁；已有补丁仍必须走沙箱验证与人工审批，无补丁则展示受阻结果。这个机制处理响应格式，不将供应商鉴权/网络失败当作格式错误重试。

新文件的标准补丁格式是 `{path,content}`，不要求先读取不存在的文件。兼容 `{path,old_text:"",new_text:"完整源码"}`，但仅当目标不存在时转换为新建；不能借此覆盖已有文件、穿越目录或跟随符号链接。字段不合法、缺少新建内容、已有文件未读分别记录不同错误类别。日志只增加协议字段名和空旧文本标记，不保存模型原文。测试生成受阻的具体原因会显示在面板；未验证通过时标题为“候选修改尚未就绪”，批准按钮保持禁用。

测试首次失败后，Hermes 将真实失败输出交回测试 Agent，最多纠正两次（合计最多三次沙箱运行，每次上限 60 秒）。纠错只能写本次方案已生成或修改的测试文件，不得改业务代码或无关测试；保留原验证入口，修正没有产生实际变化时提前停止。原有测试失败且本轮未改测试时，不会改写用户测试来迎合补丁。日志中的 `test_repair_start`、`test_repair_no_change` 和 `test_result.failure_kind` 可区分缺失依赖、收集错误和断言失败，审批窗口会显示具体失败类别及缺失模块。

模型可以用 `create_file({path,content})` 新建 Python 源码和测试文件，用 `edit_file` 精确替换或按已读取行号修改已有文件，一次最多 5 个文件。行号替换要求读取版本与当前副本一致。所有创建和修改先发生在临时副本中；审批弹窗逐文件标注「新建」「修改」「测试文件」，显示业务代码和测试的全部差异。业务文件仅增加空行或注释等、Python 语法树未变化时，修复流程直接停止，不启动测试也不提供审批。沙箱运行器会记录实际执行到的业务源码行；即使测试退出码为 0，只要任一业务文件的改动行未被执行或覆盖记录缺失，也会明确显示“未覆盖改动”并禁止写回。批准接口独立于模型工具，模型无法自行批准；拒绝不会写回。

审查模型提出的缺陷在运行复现前标为候选问题，不能当作已证实的根因。待审批界面只以实际 diff、测试入口、原始测试输出和改动行覆盖记录作为可审核事实，不把模型关于“已修复”的文字当作证据。当前未自动执行修复前对照测试，页面会明确显示“原缺陷是否复现仍待验证”。人工批准后逐文件核对写回字节，最终总结由审批和沙箱记录确定性生成，不再让模型自由撰写测试范围或残余风险。测试通过并执行改动行仍不证明所有接口、业务路径或原缺陷都已验证；未测试范围会如实标记。旧版已批准任务没有改动行覆盖记录，历史界面会提示无法追溯确认。

当前没有删除或重命名工具，也不允许清空整个文件。绝对路径、`..`、隐藏目录、密钥文件和非 Python 写入均被拒绝；不跟随符号链接，不修改硬链接。新建使用不覆盖目标的原子发布操作，即便在审批后目标突然出现，也会保留用户文件并报告冲突。批准时重新检查源码快照的文件列表与内容哈希，项目有新改动就要求重新生成，避免应用过期方案。

写回前把原文件和审批记录保存在 Hermes 启动目录的 `.hermes/backups/<方案编号>/`，页面显示备份路径。`manifest.json` 区分新建和修改。批准写回并完成或中止后，点击「一键撤销写回」可恢复本轮修改前的文件，并移除本轮新建文件；服务重启后仍可使用。撤销前会逐个核对文件仍是本轮写入的版本，若有后续改动则拒绝覆盖。普通写入失败会尝试回滚：恢复已有文件，仅移除本次新建且内容未被他人改动的文件；不递归删除目录。若进程中断或外部并发改动导致无法回滚，可根据备份与记录人工恢复。多文件写入并不是跨文件系统事务。待审批方案目前保存在内存中，服务重启后需要重新生成。

沙箱隔离的是项目执行；人工批准才授予原项目写入权限。运行生成测试默认使用 `hermes-sandbox:local` 镜像，保持禁网、只读挂载和每次 60 秒上限。更新 `sandbox/runner.py` 或 `sandbox/requirements.txt` 后需重新执行 `docker build -t hermes-sandbox:local sandbox`。零测试或全部跳过不能作为通过。测试由模型生成或修改时也会纳入审批，测试通过只表示选定范围通过，不保证覆盖所有行为；这个本地实现也不宣称已具备与 Codex 相同的安全保证。

## 确定性演示模式

未配置模型时仍可运行可复现的规则引擎演示：

```bash
# 单次诊断：运行后输出一份报告并退出
hermes "legal-agent 最近很慢，帮我排查原因" --mode rules --scenario api_slow

# 交互模式：可以连续输入多个故障问题
hermes --interactive --mode rules --scenario api_slow
```

交互模式中输入故障描述即可诊断；输入 `exit` 或 `quit` 退出。每次提问都会创建独立事件编号，并分别保存报告和 trajectory，避免多个事故的证据混在一起。

### V0.4 多角色分诊与事件记忆

`triage` 模式由可用性、性能、变更三个固定角色检查同一轮只读采集结果，再由协调器决定哪些线索可以进入根因判断。它是可复现的规则分诊，不需要模型密钥，也不会创建多个独立模型会话：

```bash
hermes "legal-agent 为什么变慢？" --mode triage --scenario api_slow
hermes-eval --mode triage
```

每次 CLI 诊断会在 `--output-dir`（默认 `artifacts/`）中保存 `incidents.sqlite3`。事件索引只包含服务名、场景或实时来源、结构化症状、诊断状态、时间和报告路径；原始提问、日志和工具输出仍只在当次 trajectory 中。之后同一服务、同一来源的相似症状会在新报告中列出，供人工回看，**不会提高本次诊断置信度或直接触发修复**。可用以下命令查看或暂停索引：

```bash
hermes --history --service legal-agent --backend scenario
hermes "只做本次诊断" --mode triage --no-memory
```

查询实时事件时使用 `--backend live --service <目标服务>`；自定义 `--output-dir` 后，诊断与历史查询应使用同一目录。索引数据库仅当前本机用户可读写；报告和 trajectory 的敏感信息仍按原有文件管理要求处理。网页项目会话记忆与这里的 SRE 事件索引相互独立。

### V0.5 平台观测（显式启用）

`hermes` CLI 的实时诊断可额外采集 Kubernetes、Prometheus 和 Grafana。未提供参数时不会访问这些平台。参数必须指定采集目标；演示场景和 `rules` 模式不使用这些集成。`triage` 将成功读取的结果列入“平台观测”分诊，`agent` 只会看到本次已启用的工具。两者都不会依据单一抓取或规则配置自动执行修复。

```bash
# 按实际环境填写 context、namespace、selector、job 和地址；以下仅是示意
export HERMES_GRAFANA_TOKEN='你的 Grafana 服务账号令牌'
hermes "hermes-web 响应变慢" --backend live --mode triage \
  --service hermes-web --container hermes-web --health-url http://127.0.0.1:8765/health \
  --kube-context prod --kube-namespace hermes --kube-selector app=hermes-web \
  --prometheus-url https://prometheus.example.com --prometheus-job hermes-web \
  --grafana-url https://grafana.example.com --grafana-token-env HERMES_GRAFANA_TOKEN
```

- Kubernetes 仅执行指定 context、namespace 和 label selector 的 `kubectl get deployments,pods -o json`。运行用户需已配置 kubeconfig 并具备相应资源的读取权限；不会执行 `apply`、`delete` 或 `rollout`。
- Prometheus 只对指定 job 查询瞬时 `up` 指标。`up=1` 仅表示抓取成功，不证明应用健康；空结果也不是健康证据。
- Grafana 使用环境变量中的服务账号令牌读取已配置告警规则的摘要。规则列表**不是当前触发告警列表**，不会把规则查询配置或令牌写入报告。令牌需有告警规则读取权限。
- 远程 Prometheus/Grafana 地址须用 HTTPS；只有 localhost、127.0.0.1、::1 可用 HTTP。HTTP 请求不跟随重定向，单次超时默认 5 秒，响应最多 128 KiB，输出最多 50 项。失败会作为采集错误留下记录，不会伪装成正常状态。

目前没有真实集群或服务地址的端到端验证；上线前请先用只读凭据在目标环境核对 label、job、网络和 Grafana 权限。这些只读采集也可在上文所述的 `hermes-web`「运行诊断」任务中显式启用；原有代码审查与修改流程不受影响。

默认演示场景稳定复现了一个可信的 AI 推理事故：

| 信号 | 证据 |
| --- | --- |
| 用户症状 | API 延迟：800 ms → 4200 ms |
| 健康检查 | HTTP 200，但 `latency_ms=4200` |
| GPU | 77,210 / 81,920 MB 显存，94% 利用率 |
| 日志 | 请求排队与 GPU 显存压力告警 |
| Git / 配置 | 最近发布将 `batch_size: 16 → 64` |

Hermes 会得出有依据的根因和最小回退方案，然后明确停在“等待用户批准”。它不会修改配置，也不会重启容器。

每次运行都会在 `artifacts/` 中产生：

- `*-report.md`：面向人的中文事件报告
- `*-trajectory.json`：工具调用、结果、状态转换、诊断与操作记录，可用于后续评测

可用 `hermes --list-tools` 查看工具白名单；`--scenario api_500` 可查看“HTTP 500 与明确的缺失环境变量日志关联诊断”的行为。若 5xx 没有对应日志或容器证据，Hermes 仍会安全停止，不会编造根因。

## Docker 故障实验环境

PRD 中的演示环境已落地为一个轻量 Docker Compose 服务。它不是生产环境模拟器，而是用于稳定复现 API 慢、API 500 和恢复正常三种情况；状态文件通过 volume 挂载到容器，注入故障不需要重建镜像。

```bash
# 终端 A：启动演示服务
docker compose -f demo/docker-compose.yml up --build

# 终端 B：注入慢接口故障
python demo/inject_fault.py --scenario api_slow

# 确认服务已变慢（约 4.2 秒返回）
curl -i http://localhost:8000/health

# 恢复正常状态
python demo/inject_fault.py --scenario normal
```

故障注入仅改写 `demo/runtime/state.json`，不会执行容器删除、重启、停止进程或任何宿主机变更命令。可用场景为 `normal`、`api_slow`、`api_500`。

### V0.2：人工审批的受控运维变更

`hermes` 诊断进程及模型工具仍然只能读取；需要实际恢复演示服务时，由运维人员在终端单独运行 `hermes-change`。升级后先重新执行 `pip install -r requirements.txt`，以安装新命令。以下示例假定演示容器正在运行、`demo/runtime/state.json` 已由故障注入脚本生成：

```bash
python demo/inject_fault.py --scenario api_slow
hermes-change --policy demo/change-policy.json plan --service legal-agent \
  --changes '{"scenario":"normal","status_code":200,"delay_seconds":0.1,"batch_size":16,"log_message":"INFO request completed normally batch_size=16"}'
hermes-change --policy demo/change-policy.json approve PLAN_ID
hermes-change --policy demo/change-policy.json apply PLAN_ID
hermes-change --policy demo/change-policy.json show PLAN_ID
```

`plan` 只读取当前配置与容器身份，输出修改前后字段；`approve` 展示计划并要求手工输入服务名，随后仅显示一次有效期十分钟的令牌；`apply` 从终端安全读取令牌，原子消费后再次检查策略、配置和容器是否变化。通过检查后，命令只修改策略白名单内的 JSON 字段、重启指定 Docker 容器，并最多检查三次本机 HTTP 健康状态、延迟和已映射字段。结果可用 `show` 追溯。每一步须使用同一 `--policy` 与 `--state-dir`（默认为 `.hermes/remediation`）。令牌失效或检查冲突时需重新生成计划，不能重用原令牌。

原配置备份保存在 `.hermes/remediation/backups/<计划 ID>.json`，命令返回备份路径。若重启或健康检查失败，**不会自动回滚**：先核对现场，再根据备份人工恢复或生成新的受控计划。示例策略仅允许 `legal-agent` 的五个演示字段，其中日志文案只能写为正常状态的固定值；实际服务须由运维人员另建白名单策略，且健康检查限本机 HTTP。此命令不接受模型生成的审批令牌或任意 Shell 命令，也不提供容器删除操作。服务重启可能中断请求，请在适当维护窗口执行。

Docker 环境启动后，可让 Hermes 读取真实的 HTTP 与 Docker 日志（其余主机采集项若不可用，会在报告中如实说明）：

```bash
hermes "legal-agent 为什么变慢了？" \
  --mode rules \
  --backend live \
  --service legal-agent \
  --container legal-agent \
  --health-url http://localhost:8000/health
```

## 本机只读采集

除了演示场景，还可以通过固定的、无 Shell 拼接的命令读取本机状态：

```bash
hermes "检查本机 legal-agent 是否正常" --mode rules --backend live \
  --service legal-agent --container legal-agent --health-url http://127.0.0.1:8000/health
```

本机模式只会尝试采集系统负载、NVIDIA GPU、Docker、HTTP 健康检查和 Git 差异。Linux 主机 CPU 使用率由 `/proc/stat` 短时间采样得到；其他系统单独展示一分钟负载估算，不把它当成真实 CPU 使用率进行归因。Docker 同时列出运行中和已停止的容器，运行中容器附带 `docker stats` 的 CPU、内存数据；资源统计失败时仍保留容器状态。容器 stdout 和 stderr 日志都会进入最近日志证据。Git 返回最近五次提交，并只从最新已提交的 JSON/YAML/TOML/INI/CFG 文件差异中提取 `batch_size` 变化。环境未安装 Docker、没有 NVIDIA GPU、服务不可访问等情况会如实写入报告，且诊断会因关键证据缺失停止。

实时诊断（包括 `--interactive`）必须同时显式传入 `--service`、`--container` 和 `--health-url`；缺少任一项会在采集前报错，不会沿用演示用的 `legal-agent` 或推测容器与端口。仅查询实时事件历史时只需 `--service`，不执行采集。演示场景仍默认使用 `legal-agent`。

Git 提交不等同于运行中的版本。即使仓库配置变更、GPU 压力和排队日志吻合，若未核对实际部署与运行时配置，规则诊断只把它列为中等置信度的线索，不会宣布根因已确认。Agent 模式的健康检查 URL 与容器日志目标固定为本次命令指定的 `--health-url`、`--container`；需诊断其他目标时重新指定参数。

> 本机模式仍然只有只读能力。`restart_service` 与 `edit_config` 只是已登记的危险工具，调用会在工具层被拒绝。

### 本机采集的前置条件

这些不是 `pip` 依赖，而是被诊断对象所在机器应具备的运行能力：

| 能力 | 是否必需 | 说明 |
| --- | --- | --- |
| HTTP 服务与正确的健康检查 URL | 基础诊断必需 | 例如 `http://localhost:8000/health`；`404` 是服务异常证据，不是 Python 安装问题。 |
| Docker Desktop / Docker daemon | 仅诊断容器时需要 | 启动 Docker Desktop 后，用 `docker ps` 确认可连接。 |
| NVIDIA 驱动与 `nvidia-smi` | 仅诊断 GPU 推理时需要 | Apple Silicon / 普通 Mac 没有 NVIDIA GPU，这是正常情况。 |
| 有至少一次提交的 Git 仓库 | 仅分析发布变更时需要 | 首次初始化、尚未提交的仓库没有可比较的历史版本。 |

`wps` 是桌面应用名称，不是 Hermes 当前支持的 HTTP / Docker 服务对象。若要诊断本机 WPS，应另行实现 macOS 应用进程、崩溃日志和性能采集适配器；它不应被当成 `http://wps:8000/health` 一类服务。

## 架构

```text
用户故障描述
    ↓
LLMSREAgent：模型选择下一项只读工具
    ↓
ControlledTools：程序校验工具与参数，不提供任意 Shell
    ↓
ScenarioBackend（可复现演示） / LiveReadOnlyBackend（本机只读）
    ↓
证据轨迹 → 模型假设 → 程序验证证据引用 → 报告
    ↓
修复建议（模型不会执行；人工可另用 hermes-change 生成受控变更）
```

工具边界就是安全边界。`system_metrics`、`gpu_metrics`、`docker_list`、`docker_logs`、`service_health`、`git_recent_changes`、`config_diff` 与 `git_code_review` 是只读工具。`restart_service`、`edit_config` 被定义为危险操作，并且在进入任何后端之前即被阻断。

## 安全设计

- 没有通用的 `run_shell` 工具。
- 每次只读观察及其失败都会被记录到 trajectory。
- 只有多条独立证据互相印证，才会给出高置信度根因。
- 缺少或冲突的证据会产生“未确定”报告，绝不编造结论。
- `hermes` 模型工具始终只读；V0.2 的写配置与重启仅存在于独立的人工 CLI，需白名单策略和一次性审批令牌。

### 代码审查是否需要沙箱？

需要分层处理：**只读差异审查**不需要运行代码，但仍应在只读工作区中进行，限制读取范围、返回长度，并把 Git 差异 / 日志视为不可信输入，防止提示注入。Hermes 的 `git_code_review` 正是这一层：仅调用禁用外部 diff 与分页器的受限 `git show`，最多返回 20,000 字符，绝不执行仓库内容。

**运行测试、构建、复现故障或执行脚本**则必须进入独立沙箱：临时 worktree 或容器、无默认网络、无生产密钥、CPU / 内存 / 时长限制。它与 SRE 运维变更是两个独立权限域。页面的项目测试已使用上文所述的一次性 Docker 沙箱；沙箱验证通过仍不能代替人工批准写回。

## 质量检查

诊断评测提供八个不依赖模型和 Docker 的用例，涵盖慢接口、明确配置错误、证据不足、健康检查缺失、CPU 压力、容器停止及仓库变更尚未部署等情况。升级后重新执行 `pip install -r requirements.txt`，然后运行：

```bash
hermes-eval
# V0.4 三角色分诊使用相同的预期用例：hermes-eval --mode triage
# 需要保存完整结果时：hermes-eval --output evaluation-result.json
```

输出包含每个用例的根因、置信度、是否需审批以及通过情况；任何用例不通过会返回非零退出码。用例定义在 `demo/evaluation_cases.json`，可通过 `--cases` 指定其他用例文件。评测验证的是确定性规则诊断，不代表真实服务联调或模型诊断已通过。

```bash
PYTHONPATH=src python3 -m unittest discover -s tests -v
```

审批弹窗和历史方案中的代码差异使用红色表示删除、绿色表示新增，同时展示新旧行号和增删数量。源码按纯文本显示，不会作为 HTML 执行。修改前端后刷新页面即可，无需重启服务。

前端差异展示的回归测试使用 Node.js 内置测试工具，无需安装 npm 依赖：

```bash
node --test tests/test_diff_ui.cjs
```

测试覆盖：端到端慢接口诊断、模型自主工具选择、伪造证据拦截、危险重启工具拦截、代码审查输入限制、证据不足时的安全停止，以及 V0.2 的令牌重放、配置冲突、白名单和健康检查失败。
